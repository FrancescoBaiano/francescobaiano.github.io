// 02 — THE CHALLENGE

One application, many audiences, several headsets.

Headset Party had to work for very different situations: a group watching the same film, a spectator choosing a theatre show, a museum visitor browsing content. On top of that, it had to be installed and kept up to date on headsets from two different platforms.

01 / PUBLIC SCREENINGS

Preselected films

Projections for an audience, with films chosen in advance.

02 / PILLOLE DI TEATRO

Theatre with leading comedians

A version created with well-known comedians, where the viewer chooses the show to watch.

03 / MUSEUMS & EVENTS

Content picked by the visitor

Projections for a sporadic audience, such as museum visits, where the visitor chooses what to see.

// 03 — PILLOLE DI TEATRO IN ACTION

// 04 — HOW IT WORKS

One build, configured by JSON.

The app reads its setup from JSON files rather than having it hard-coded, so the same application can serve every context.

STEP 01

Describe the content

JSON defines where each film is located, its description and how it should be viewed.

STEP 02

Choose the mode

JSON also sets how the app behaves: content selection by the viewer, remote control by an operator, or Pillole di Teatro.

STEP 03

Run on any headset

The same app is deployed on Quest 2, Quest 3, Quest 3S and Pico G2.

// 06 — TECHNICAL REFLECTION

What this project demonstrates.

Headset Party shows what it takes to keep a VR product alive after the first release: maintaining one codebase across several headsets and two platforms, updating devices in the field, and supporting live events where nothing can go wrong in front of the audience.
